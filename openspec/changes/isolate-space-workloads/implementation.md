## Protected execution handoff

Scaling hands SDK Base a host-created `ProtectedSpaceApproval` after authenticating Entry and checking the worker's current approval file. `PipelineExecutor::verify_protected_space` checks expiry, exact manifest bytes and the phase-specific controller shape. `VerifiedSpaceExecution` retains the approval and worker-configured controller path independently of the parsed manifest. The controller shape excludes manifest-selected Python environments, source checkout paths, alternate plugin inputs, host placement and extra workload parameters.

An executor created with `for_protected_spaces` denies ordinary plugin resolution, ordinary session creation and warm-pool construction before provisioning. The protected Runner creates this executor at startup. On Linux, a Runner with the opt-in CPU runtime configured uses the verified handoff below for sandbox startup.

The Windows build with `loadable,python-source-plugin` passed three protected execution tests and the three existing source-Python wire tests. The protected tests cover both phases, expired or changed requests, environment and plugin overrides with matching digests, and refusal before ordinary loaders or warm sessions are called. Scaling exercised the SDK Base verifier over the real mutual TLS listener. [Scaling verification](../../../../remotemedia-scaling/openspec/changes/isolate-space-workloads/implementation.md)

## Protected preparation controller

On Linux x86-64 with `loadable,python-source-plugin`, `VerifiedSpaceExecution::start_preparation` opens a private one-shot session for an isolated CPU prepare grant. SDK Base accepts the released local source-Python `PrepareSpaceNode`, derives the request from the approved repository, commit and target, and takes the checkout path, policy file and preinstalled Python executable from worker settings. It invokes the worker policy check before resolving the controller and again before starting it. The selected interpreter bypasses dependency probes and managed installation. Only the trusted owner can submit the one request or receive the descriptor.

SDK Base supplies the owner from `VerifiedSpaceExecution` in the private controller's preparation settings. This lets the controller evaluate an exact owner grant against the worker policy. The protected verifier rejects a manifest that supplies its own preparation settings or attempts to set an owner. Four focused Linux SDK tests passed, including the preparation owner override case for both signed phases. Three fixture-dependent tests were skipped in that command. A separate managed fixture exercised the real source controller and isolated Gradio with an owner-only policy.

SDK Base bounds the descriptor at 1 MiB and checks its repository, commit, source digest format and canonical checkout containment. The preparation handle retains the Python controller and explicitly joins its process after the router stops. A real Entry and Runner fixture fetched the approved public Hugging Face commit. A second fixture handed a pinned local Git checkout to protected Gradio and verified that revoking an active preparation left no controller descendants while Runner remained alive. [Spaces verification](../../../../huggingface-spaces-runner/openspec/changes/isolate-space-workloads/implementation.md)

The protected preparation supervisor reserves a cgroup v2 child under the worker's dedicated preparation parent. The parent must have finite CPU, memory and process limits with swap disabled. Each controller reserves its full process allowance from the shared parent before startup. SDK Base binds a membership file descriptor to the private Python executor and joins the child cgroup before exec. Shared-worker selection and Docker are excluded from this path. Forked Git helpers and other descendants inherit the controller's scope. Cleanup observes the kernel's population state before removing a scope. New reservations recover abandoned scopes under a lock and skip scopes still owned by a live Runner. [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)

Protected preparation verifies a dedicated `ext4` or `tmpfs` checkout mount before resolving the controller and before launching Python. The kernel mount table must identify the opened directory as the filesystem root without aliases or nested mounts. The filesystem requires private Runner ownership, finite block and inode capacities, and writable `nodev,nosuid,noexec` options. Its total allocatable block capacity must fit the worker's `checkout_bytes`. The check reads the capacity from the opened mount. An ordinary cache directory cannot supply this enforcement. [Linux mount information](https://docs.kernel.org/filesystems/proc.html) · [tmpfs allocation limits](https://docs.kernel.org/filesystems/tmpfs.html)

## Artifact registration and staging

`SpaceArtifactRegistry` uses an operator-owned directory with a dedicated content store, atomic registration records, and separate per-run staging directories. The trusted publisher imports bounded streams by SHA-256 and byte count and registers the exact `workload-artifact.json` and `source-tree.json` bytes against the launch scope. Registration checks repository, commit, target, Python ABI, policy, paths and closure before publishing. Store the directory outside workload access and restrict its ACLs or permissions to the trusted processes.

An acquisition rechecks the registration and copies the exact verified source, wheels, and model files into an independent lease. Active leases keep their copied bytes if the content store changes. Failed and normally released leases are removed. The provider must retain the lease through confirmed teardown and expose its inputs through read-only mounts. Startup reconciliation remains open.

On Unix, the lease root stays private at `0700`. The source, wheel and model directory trees use `0755` so a different guest UID can traverse them after each tree is mounted read-only. Files are readable and retain only their verified execute bits. The four focused Linux artifact tests passed with worker umask `077`, including exact mode checks for the lease root, nested trees and files.

`receive_publication` accepts a bounded header and streams the closure in inventory order. It verifies and imports every file before returning its readiness byte. The worker rechecks launch policy, then sends a commit byte and closes the stream. The registry installs the record atomically after receiving both. A denied or interrupted publication may retain verified store blobs for reuse. Registration stays absent until the commit succeeds.

All 27 Linux bundle-deployment library tests and four focused Windows registry tests passed. A Windows fixture generated the records with the Spaces Python worker code, including a Unicode source filename, and published those bytes through the native Runner subcommand. The live Runner denied the serve request before registration and reached the runtime availability check after publication.

## Isolated Linux CPU handoff

The native SDK fixture denies an unregistered artifact scope, an unsupported target, a guest Python ABI mismatch, and a verified approval for a different run. A same-size store mutation after authorization fails staging with a digest mismatch and releases the partial bundle. The test restores the registered bytes, stages a new bundle, changes the store again, and reads the original verified bytes through the run-bound guest relay. The authorization and bundle-deployment tests cover manifest overrides, exact registration, and concurrent leases surviving a failed copy.

The `protected-space-runsc` feature stages a registered closure directly into a gVisor reservation. SDK Base derives the registration scope from the verified serve approval. It checks the staged Python ABI against the operator's guest image configuration and reads the SDK and entry file from the verified artifact. The operator configures the trusted launcher in that image. It receives the SDK, the absolute guest entry path, and the loopback port as arguments.

The caller must present current verified admission when starting a staged run. The launch and gateway stream capability both match the entire original approval, including the run, owner, policy, manifest and artifact digest. The provider bounds the workload lifetime by the earlier of the configured limit and the approval expiry and retains the artifact through teardown. The Linux Runner can select the cancel-safe wait against stop and policy revocation while it owns the run. Gateway authorization still needs to use that run's private stream capability.

The Linux integration fixture used pinned gVisor on WSL2 with worker `umask 077` and registered a synthetic source, wheel and model closure. It refused an unregistered policy, an incompatible Python ABI, and a mismatched run at launch and relay open. The matching grant started a guest that confirmed all three byte sequences. Stopping the run closed the stream and cleared the sandbox reservation. The three protected manifest and admission regression tests also passed.

For the Linux fixture, set `RM_SPACE_TEST_RUNSC` to the pinned runtime and `RM_SPACE_TEST_CGROUP` to an exclusive delegated test subtree with the required controllers enabled. With a static C toolchain available, run `cargo test -p remotemedia-sdk-base --features protected-space-runsc --lib registered_lease_launches_in_run_bound_sandbox -- --ignored`.

`IsolatedSpaceRuntime::reconcile_abandoned` runs the provider's startup reconciliation without constructing a workload runtime or opening its artifact registry. The pinned provider takes both exclusive locks before deleting abandoned units. The native managed crash fixture verified that the offline entry point refused a live provider and removed the bundle and cgroup after Runner exited. The lease now includes the approved Python ABI and wheel SHA-256 map in the read-only wheel mount. It also stopped the sandbox and checked reservation cleanup. The 27 Linux bundle-deployment tests passed with worker `umask 077`.
